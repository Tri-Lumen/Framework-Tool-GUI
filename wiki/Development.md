# Development

## Setup

```bash
pip install -r requirements.txt      # PySide6-Essentials, the one dependency
python3 framework_gui.py             # or: python3 -m frameworkgui
```

The app is the `frameworkgui` package; `framework_gui.py` at the root is a
launcher that imports it, and is what every packaging path points at.

Linux also needs the libraries Qt's wheels link against:

```bash
sudo apt install libegl1 libgl1 libxkbcommon-x11-0 libxcb-cursor0
```

## Tests

```bash
python3 -m unittest discover tests -v                            # no display needed
QT_QPA_PLATFORM=offscreen python3 -m unittest discover tests -v  # including GUI
python3 -m ruff check .
```

They are fast (a few seconds) and they are what catches the failure modes
that only appear in a packaged build. Run them before changing `parsers.py`
or any gating logic.

**Watch for silent skips.** The GUI tests skip themselves when there is no Qt
platform plugin, and on Windows (the stub CLI is a POSIX script). A green run
that skipped everything looks identical to a green run that tested
everything — check the count.

### What each suite guards

| Suite | Guards |
| --- | --- |
| `test_parsers` | Every regex, against samples from upstream's `EXAMPLES.md` |
| `test_commands` | That every flag the app can issue is one framework_tool publishes, and that enum-valued flags only get values it accepts |
| `test_navigation` | The gating table, and that every icon path spells its commands out |
| `test_iconpaths` | The icon path language, the arc geometry, and every icon the app ships |
| `test_packaging` | That the package and its assets reach every packaging path, that the launcher is the only Python file at the root, and that only the UI layer imports PySide6 |
| `test_smoke_gui` | A real app against a stub CLI: which controls survive gating, and that a busy app strands no UI |
| `test_deps` | Every install plan, the release-asset ranking, and the cleanup step |

## Building

**Windows** — `windows/build.bat` runs PyInstaller and produces
`windows/dist/FrameworkGUI.exe`. It **only builds**; it installs nothing.
`windows/install-exe.cmd` is the separate step that copies the exe locally
and creates the Start Menu shortcut. Keep those two distinct — build once
centrally, deploy per device.

`windows/installer.iss` compiles the installer with Inno Setup.

**Linux** — `flatpak/README.md` has the build steps.

### Two things that will waste your afternoon

**PyInstaller and flatpak-builder both fail on network paths.** `build.bat`
copies sources to `%TEMP%` first and copies the result back. flatpak-builder
needs OSTree hardlinks and xattrs that network filesystems do not support,
and there is no code-level workaround.

**PowerShell's execution policy blocks `.ps1` files launched from a network
share.** Every `.ps1` in `windows/` has a matching `.cmd` wrapper. Point
people at the `.cmd` files.

## Adding a module or an asset

Put it in `frameworkgui/` and the two Windows paths carry it on their own —
both copy the package directory rather than a list of filenames, which is
what stops them falling behind. The Flatpak manifest is the exception:
flatpak-builder's `file` sources are one file each, so a new module needs
two lines in
`flatpak/io.github.frameworkgui.FrameworkGUI.yml` — the `install -Dm644`
command **and** the entry in `sources:`.

`tests/test_packaging.py` fails until you do. A miss there produces a build
that dies with `ModuleNotFoundError` on launch, which is invisible from a
source checkout where the import works.

Data files have one extra wrinkle: PyInstaller's `--onefile` unpacks bundled
data into a temporary tree it advertises as `sys._MEIPASS`, so
`device_images.asset_root()` and `app_icon.asset_root()` look there first.
Load a data file any other way and it works from a checkout and not from the
exe.

## Releasing

Publishing a GitHub Release (tag `vX.Y.Z`) triggers
`.github/workflows/release.yml`, which builds and attaches three assets:

| Asset | Built by |
| --- | --- |
| `FrameworkGUI-Setup.exe` | `windows/installer.iss` via Inno Setup |
| `FrameworkGUI.exe` | `windows/build.bat` via PyInstaller |
| `FrameworkGUI.flatpak` | `flatpak/…FrameworkGUI.yml` via flatpak-builder |

**Those filenames are a contract** — the README links
`/releases/latest/download/<name>` for each and `test_packaging.py` fails if
the workflow and the README disagree.

The version comes from the tag with any leading `v` stripped. A manual
`workflow_dispatch` run builds everything under `0.0.0-dev` and skips only
the upload — use it to rehearse.

## Screenshots

The images in `wiki/screenshots/` are generated by driving the app against a
stub `framework_tool` under `QT_QPA_PLATFORM=offscreen`, with `detect_cpu()`
patched so the capture carries the simulated board's CPU rather than the
build machine's.

Grab **after** letting the event loop turn. Screenshots taken too early come
out blank — the geometry is right, the paint has not happened.

## Things deliberately not done

- **Persisting power limits across reboots** — needs a background process.
- **Driving ThrottleStop** — it has no command line.
- **Running downloaded vendor installers** — the app downloads and stops.
- **UI for the flashing commands** — they can brick hardware.

These are decisions, repeated across the project, not oversights. If one
comes back it is a decision to reverse, not a small feature.
